APPENDIX 01
별첨 1. 의사소통 계획
1. 보고 체계
No 보고 구분 보고 주기 보고자 → 수신자 주요 내용
1 일일 스탠드업 매일 (15분) 팀원 → PM 전일 작업 완료, 금일 계획, 블로커 공유
2 주간 진행 보고 매주 금요일 PM → 스폰서 스프린트 진행률, 이슈, 다음 주 계획
3 스프린트 리뷰 2주/회 PM → 전체 스프린트 결과 시연, 피드백 수렴
4 마일스톤 보고 분기/회 PM → 스폰서 Phase 완료 산출물, KPI 달성 현황, 리스크 평가
5 이슈 에스컬레이션 즉시 팀원 → PM → 스폰서 긴급 이슈 발생 시 즉시 보고 및 대응
6 월간 운영 보고 월 1회 PM → 스폰서 서비스 가동 현황, 사용자 지표, 장애 이력
2. 회의 계획
No 회의명 주기 시간 참석자 안건
1 일일 스탠드업 미팅 매일 15분 전체 개발팀 작업 진행 상황, 블로커
2 스프린트 플래닝 2주/회 2시간 PM + 개발팀 백로그 우선순위, 스프린트 목표, 작업 할당
3 스프린트 리뷰 & 회고 2주/회 1.5시간 PM + 개발팀 + 스폰서 시연, 피드백, 프로세스 개선
4 기술 설계 리뷰 수시 1시간 백엔드 + 프론트 + AI API 설계, DB 스키마, 아키텍처 변경
5 QA 리뷰 미팅 주 1회 1시간 QA + 개발팀 테스트 결과, 결함 분석, 릴리즈 준비
6 마일스톤 리뷰 Phase별 2시간 전체 + 스폰서 Phase 산출물 검토, 다음 Phase 계획 승인
의사소통 도구: Slack (일반 소통) · Jira (이슈/스프린트 관리) · Confluence (문서화) · GitHub (코드 리뷰) · Zoom (원격 회의)

APPENDIX 02
별첨 2. 프로젝트 관리 계획
1. 범위 관리 계획
항목내용
범위 정의개발계획서 2장(프로젝트 개발 내용)에 명시된 6개 핵심 기능을 개발 범위로 정의
WBSPhase별 작업 분할 구조(WBS)를 Jira 백로그로 관리, 스토리 포인트 추정
범위 변경 통제모든 범위 변경은 Change Request(CR) 문서 작성 → PM 검토 → 스폰서 승인 절차
제외 범위모바일 네이티브 앱(P4 검토), 실시간 화상 강의, 교사/학부모 포털은 개발 범위에서 제외
검수 기준각 기능별 acceptance criteria를 스토리에 명시, QA가 검증 후 릴리즈
2. 일정 관리 계획
항목내용
스프린트 주기2주 스프린트, 총 24회 스프린트 (12개월)
일정 추적Jira Sprint Board, Burndown Chart를 주간 보고에 포함
마일스톤M1(3개월) MVP / M2(6개월) 기능확장 / M3(9개월) 고도화 / M4(12개월) 상용화
지연 대응스프린트 지연 시 우선순위 재조정, 범위 축소 또는 일정 연장을 PM이 판단하여 스폰서 보고
버퍼각 Phase별 일정의 15%를 버퍼로 확보 (예상치 못한 이슈 대응)
3. 품질 관리 계획
항목내용
코드 리뷰모든 PR은 1명 이상 리뷰어 승인 후 머지 (GitHub Pull Request)
테스트 커버리지백엔드 단위 테스트 커버리지 80% 이상, 프론트엔드 핵심 로직 70% 이상
통합 테스트각 스프린트 종료 시 통합 테스트 수행, 회귀 테스트 자동화
AI 콘텐츠 품질AI 생성 문제/요약은 관리자 검수 큐를 거쳐 승인 후 노출. 정답률 기반 품질 모니터링
성능 기준API 응답 P95 3초 이내, 페이지 로드 2초 이내, AI 생성 P95 5초 이내
정적 분석SonarQube / ESLint 정적 분석을 CI에 통합, Critical 이슈 0건 유지
4. 의사소통 관리 계획

별첨 1(의사소통 계획)에 상세 명시. 주요 원칙:

  • 모든 의사결정은 문서화하여 Confluence에 기록
  • 이슈는 24시간 내 Slack에 공유, 48시간 내 대응
  • 주간 보고서는 매주 금요일 17:00까지 발송
  • 에스컬레이션 경로: 팀원 → PM → 스폰서 (긴급 시 즉시)
5. 위험 관리 계획
No 위험 항목 확률 영향 등급 대응 전략
1 AI 응답 품질 불량 중고상 프롬프트 엔지니어링 고도화, 관리자 검수 큐 의무화, 정답률 모니터링
2 AI API 비용 증가 중중중 API 호출 캐싱(Redis), 사용량 모니터링, 프리미엄 사용자에게만 고빈도 호출 허용
3 크롤링 소스 차단/변경 중중중 다중 소스 확보, 크롤링 주기 조절, 수동 입력 백업 체계
4 개발 일정 지연 중고상 Phase별 15% 버퍼 확보, 우선순위 재조정, 범위 축소 옵션
5 인력 이탈 저고중 페어 프로그래밍, 코드 문서화, 지식 공유 세션, 백업 인력 확보
6 데이터 유출/보안 사고 저고중 JWT + HTTPS, 비밀번호 bcrypt, 정기 보안 점검, 개인정보 암호화 저장
7 서버 장애/다운타임 저중하 Docker 컨테이너 자동 재시작, Nginx 헬스체크, 백업 스케줄 (일 1회)
8 교육과정 변경 저중하 교육과정 매핑 테이블 분리, 변경 시 데이터 업데이트 배치 작업
6. 소스 관리 계획
항목내용
저장소GitHub (Organization), Monorepo 구조 (backend / frontend / docs)
브랜치 전략Git Flow — main / develop / feature/* / hotfix/*
커밋 규칙Conventional Commits — feat: / fix: / docs: / refactor: / test: / chore:
PR 규칙모든 변경은 PR 생성, 1명 이상 리뷰 승인, CI 통과 후 머지
CI/CDGitHub Actions — 빌드/테스트/정적분석 자동화, develop 머지 시 자동 배포 (staging)
릴리즈main 브랜치 머지 시 production 배포, 버전 태그 부여 (SemVer)
백업Git 원격 저장소 자동 백업, DB 일일 백업 (30일 보관)
