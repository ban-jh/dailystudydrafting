# Daily Study 전체 진행 절차

> 기획부터 개발, 검증, 배포, 운영 개선까지 사용자가 단계별로 결정하고 Codex가 조사·문서화·구현을 돕기 위한 진행 기준입니다.
>
> 진행 원칙: 한 번에 한 단계씩 진행합니다. 각 단계에서 결과물을 검토하고 합의한 뒤 다음 단계로 넘어갑니다. 범위나 전제가 바뀌면 관련 문서와 완료 기준을 먼저 갱신합니다.

## 1. 목표와 진행 방식

Daily Study는 사용자가 매일 학습 자료를 받고 실제 학습을 이어가도록 돕는 서비스를 만드는 프로젝트입니다. 콘텐츠의 정확성과 안전성, 매일 안정적으로 제공되는 경험, 학습 완료 기록과 개선 가능성을 제품의 핵심으로 둡니다.

이 문서는 작업 순서를 정하는 기준입니다. 각 단계의 일정과 세부 범위는 조사와 사용자 결정 후 확정하며, 문서에 적힌 기능이나 기술을 확정 요구사항으로 간주하지 않습니다.

### 협업 루프

1. 사용자는 진행할 단계나 당면한 질문을 말합니다.
2. Codex는 저장소와 관련 문서를 확인하고, 결정이 필요한 사항은 선택지와 영향을 정리합니다.
3. 합의한 범위에 대해 문서·코드·화면 등 검토 가능한 결과물을 만듭니다.
4. 정해진 완료 기준에 따라 확인하고 결과와 남은 결정을 보고합니다.
5. 사용자가 검토·수정 방향을 정한 후 다음 단계로 넘어갑니다.

사용자가 이미 결정한 내용은 반복해서 묻지 않습니다. 구현·테스트 범위도 해당 단계에서 합의한 사용자 여정과 변경 사항에 맞춥니다.

### 전문가 에이전트 구성

프로젝트 리드는 전체 목표·우선순위·결정 사항을 관리하고, 아래 전문가 에이전트에게 해당 영역의 조사·설계·구현·검토를 맡깁니다. 에이전트는 필요한 단계에서만 참여합니다. 사용자 요구와 우선순위의 최종 결정은 사용자와 프로젝트 리드가 하며, 전문가 제안은 기존 요구사항 및 다른 영역의 영향과 함께 통합합니다.

| 에이전트 | 책임 | 주로 참여하는 단계 |
|---|---|---|
| 제품 기획자 | 사용자 문제, 요구사항, MVP 범위·우선순위와 성공 지표 | 0–3, 11 |
| 교육·학습 설계자 | 학습 목표·흐름, 난이도, 콘텐츠의 교육적·연령 적합성 | 1–4, 8–9 |
| UX/UI 디자이너 | 핵심 여정, 화면·상태 설계, 모바일·접근성 및 사용성 | 3–4, 7, 9 |
| 기술 아키텍트 | 기술 선택, 시스템 경계, 데이터·API·보안·운영 구조 | 2–6, 10 |
| 프론트엔드 개발자 | 웹 앱 기반, 화면·상태 구현, API 연동과 브라우저 동작 | 6–7, 9 |
| 백엔드 개발자 | 서버 기반, API·도메인 로직·저장·권한과 운영 기능 | 5–8, 10 |
| QA·테스트 전문가 | 인수 기준 검토, 위험 기반 검증, 결함 재현·추적 | 2–3, 6–10 |

**협업 규칙**

- 먼저 담당 전문가가 독립적으로 분석하고, 경계가 겹치는 결정은 관련 전문가끼리 검토 의견을 교환합니다.
- 제안에는 근거, 전제, 영향 범위, 미해결 질문을 함께 적습니다. 서로 다른 의견은 임의로 하나를 지우지 않고 선택지와 절충점을 정리합니다.
- 한 에이전트가 다른 영역의 요구를 확정하지 않습니다. 예를 들어 기술 아키텍트는 구현 선택지를 제시하고 제품 범위는 제품 기획자와 사용자가 결정합니다.
- 파일 변경은 범위가 겹치지 않게 조정하고, 통합 담당이 문서·API·화면·구현 간 일관성을 검토합니다.
- QA는 요구사항과 인수 기준을 초기에 구체화하고, 합의된 시점과 범위에서 검증합니다.
- 에이전트는 필요할 때 작업에 참여하는 협업자이며, 항상 백그라운드에서 실행되는 상시 서비스가 아닙니다. 다음 작업에서 필요하면 같은 역할을 다시 호출합니다.

## 2. 전체 단계 요약

| 단계 | 이름 | 주요 결과물 | 다음 단계로 넘어가는 조건 |
|---|---|---|---|
| 0 | 현재 상태와 목표 정리 | 프로젝트 현황, 문제 정의, 성공 기준 | 무엇을 누구를 위해 해결할지 설명할 수 있음 |
| 1 | 사용자·시장·콘텐츠 조사 | 사용자 시나리오, 콘텐츠 원칙, 근거와 가정 | 주요 사용자와 학습 문제에 대한 합의 |
| 2 | 제품 범위와 MVP 결정 | 우선순위 기능 목록, 제외 범위, MVP 성공 지표 | 첫 출시에서 검증할 핵심 가치가 명확함 |
| 3 | 요구사항과 정책 정의 | 사용자 여정, 요구사항, 콘텐츠·개인정보 정책 | 요구사항과 예외 상황을 검토할 수 있음 |
| 4 | UX·화면 설계 | 화면 흐름, 상태별 화면, 반응형·접근성 기준 | 핵심 여정의 화면과 동작에 합의함 |
| 5 | 기술·데이터 설계 | 아키텍처, 데이터 모델, API, 보안 결정 | 구현 순서와 주요 기술 위험이 정리됨 |
| 6 | 개발 기반 구축 | 실행 가능한 앱 뼈대, 환경 설정, 기본 자동화 | 개발 환경에서 기본 흐름을 실행할 수 있음 |
| 7 | 기능별 구현 | 동작하는 기능 단위, 문서와 코드 변경 | 합의한 인수 기준을 기능별로 충족함 |
| 8 | 콘텐츠 공급·검수 구축 | 콘텐츠 생성/수집, 검수와 게시 흐름 | 품질 기준에 맞는 자료를 반복 공급할 수 있음 |
| 9 | 통합 검증·사용성 확인 | 검증 결과, 결함 목록, 수정 내역 | 출시 차단 결함이 없고 핵심 여정이 통과됨 |
| 10 | 출시 준비·배포 | 운영 환경, 백업·복구와 배포 절차 | 배포·관측·복구 방법을 확인할 수 있음 |
| 11 | 운영·개선 | 지표, 사용자 피드백, 개선 우선순위 | 운영 데이터를 다음 개선 주기에 반영함 |

## 3. 단계별 진행 방법

### 0단계. 현재 상태와 목표 정리

**할 일**

- 저장소, 기존 기획 문서, 구현 상태, 미결정 사항을 확인합니다.
- 서비스의 대상 사용자, 해결하려는 문제, 현재 제약을 한 문단으로 정리합니다.
- 초기에 확인할 수 있는 성공·실패 신호를 정합니다.

**산출물**: 프로젝트 현황 요약, 목표와 제약, 결정이 필요한 질문 목록.

**완료 기준**: 현재 문서 중 유효한 결정과 검토가 필요한 가정을 구분하고 다음 논의 주제를 합의합니다.

### 1단계. 사용자·시장·학습 콘텐츠 조사

**할 일**

- 학생, 보호자, 관리자 등 사용자별 필요와 환경(학년, 기기, 학습 시간, 접근성)을 파악합니다.
- 매일 학습을 시작하고 완료하는 데 필요한 동기와 방해 요인을 조사합니다.
- 교육과정·자료 출처, 사용 권한, 콘텐츠 정확성 검수 방식, 연령에 적합한 표현을 확인합니다.
- 확인된 사실, 가설, 아직 모르는 점을 분리합니다.

**산출물**: 사용자 유형 및 시나리오, 학습 목표, 콘텐츠 출처·품질 원칙, 조사 근거.

**완료 기준**: 첫 버전에서 가장 중요한 사용자와 그 사용자의 핵심 학습 문제에 동의합니다.

### 2단계. 제품 범위와 MVP 결정

**할 일**

- 핵심 여정 하나를 먼저 선택합니다. 예: 오늘의 학습 자료 확인 → 학습 → 문제 풀이 또는 완료 기록.
- 기능을 필수·후속·제외 범위로 나눕니다.
- 사용자 가치, 구현 부담, 콘텐츠 운영 부담, 위험을 함께 보고 우선순위를 정합니다.
- 성공 지표를 정의합니다. 예: 자료 제공 성공률, 학습 시작/완료율, 주간 재방문, 문항 오류 신고율.
- 계정·알림·보상·AI 생성 등 선택 기능이 MVP에 실제 필요한지 결정합니다.

**산출물**: MVP 범위, 사용자 여정 초안, 지표 정의, 제외 범위와 이유.

**완료 기준**: MVP가 검증할 가설과 첫 출시에서 제공하지 않을 기능을 설명할 수 있습니다.

### 3단계. 요구사항과 정책 정의

**할 일**

- 기능 요구사항과 품질 요구사항(응답성, 안정성, 접근성, 보안)을 작성합니다.
- 학습 콘텐츠의 단위·난이도·정답·해설·출처·검수 상태를 정의합니다.
- 자료가 없거나 생성 실패, 중복 자료, 잘못된 정답, 사용자의 오답·중단 같은 예외를 정합니다.
- 학생 계정과 개인정보의 수집·보관·삭제, 미성년 사용자 보호, 알림 동의 등 필요한 정책을 검토합니다.
- 각 요구사항을 확인 가능한 인수 기준으로 바꿉니다.

**산출물**: 요구사항 목록, 사용자 여정, 콘텐츠 스키마 초안, 인수 기준, 정책 결정 목록.

**완료 기준**: 핵심 흐름과 주요 예외 상황을 화면·데이터·정책 관점에서 검토할 수 있습니다.

### 4단계. UX·화면 설계

**할 일**

- 핵심 사용자 여정의 화면과 화면 간 이동을 설계합니다.
- 로딩, 빈 상태, 오류, 성공, 오답 등 상태별 화면을 정의합니다.
- 모바일 우선 레이아웃, 키보드 조작, 명도 대비, 글자 크기와 터치 영역을 확인합니다.
- 학습을 방해하지 않는 알림·보상·진행 표시 방식을 결정합니다.
- 구현 전 화면 프로토타입을 검토하고 피드백을 반영합니다.

**산출물**: 화면 목록, 흐름도 또는 프로토타입, 상태별 동작, 디자인 기준.

**완료 기준**: 사용자가 오늘의 자료를 찾아 학습을 마치는 흐름을 화면 기준으로 따라갈 수 있습니다.

### 5단계. 기술·데이터 설계

**할 일**

- 기존 설계와 MVP 요구사항의 차이를 확인하고 기술 선택을 재검토합니다.
- 프론트엔드·백엔드 경계, API, 데이터 모델, 콘텐츠 버전·게시 상태를 설계합니다.
- 인증·권한, 비밀정보, 개인정보, 로그, 백업, 장애 대응을 설계합니다.
- 정기 자료 생성/가져오기, 검수, 게시, 사용자별 제공 시각과 중복 방지 방식을 정합니다.
- AI 사용 여부와 공급자, 비용 한도, 실패 대체 경로, 품질 검수 책임을 결정합니다.
- 기술 위험과 단계적 구현 순서를 기록합니다.

**산출물**: 갱신된 아키텍처·ERD·API 명세, 보안 결정, 개발 순서와 위험 목록.

**완료 기준**: 핵심 여정에 필요한 데이터를 어떤 시스템이 만들고 검증·저장·제공하는지 설명할 수 있습니다.

### 6단계. 개발 기반 구축

**할 일**

- 저장소 구조와 로컬 개발 실행 방법을 정리합니다.
- 설정과 비밀정보를 코드에서 분리하고 개발·테스트 환경을 구분합니다.
- 코드 포맷·정적 분석·빌드·필요한 자동 검증의 실행 방법을 마련합니다.
- 데이터베이스 마이그레이션, 기본 오류 처리, 로그 형식, 헬스 체크를 구성합니다.
- 최소한의 화면과 API가 개발 환경에서 연결되는지 확인합니다.

**산출물**: 실행 가능한 프로젝트 뼈대, 환경 설정 예시, 개발 안내, 기본 파이프라인.

**완료 기준**: 새 개발 환경에서 문서만 따라 기본 앱을 띄우고 간단한 요청 흐름을 확인할 수 있습니다.

### 7단계. 기능별 구현

구현은 얇은 수직 단위로 진행합니다. 한 단위에서 화면, API, 저장, 권한과 필요한 검증을 함께 완성해 사용자가 확인할 수 있게 합니다.

**권장 순서**

1. 오늘 학습 자료와 콘텐츠 조회
2. 학습 콘텐츠 상세 확인과 진행 상태 기록
3. 퀴즈 풀이·채점·해설과 학습 기록
4. 관리자 콘텐츠 작성·수정·검수·게시
5. 계정·개인화·통계 등 MVP에서 합의한 후속 기능

각 작업은 목적, 관련 요구사항, 완료 조건, 영향 파일을 먼저 확인하고 구현합니다. 결정이 필요한 범위 변경은 구현에 섞지 않고 의사결정 항목으로 올립니다.

**산출물**: 동작하는 기능, 갱신된 문서와 변경 요약.

**완료 기준**: 해당 기능의 인수 기준을 확인했고, 변경된 흐름의 검증 결과와 미해결 사항을 기록했습니다.

### 8단계. 콘텐츠 공급과 검수 구축

**할 일**

- 콘텐츠를 직접 작성·제휴 제공·허용된 자료 활용·AI 보조 생성 중 어떤 방식으로 공급할지 결정합니다.
- 출처와 사용 권한, 교육과정 적합성, 정답 정확성, 난이도, 편향·부적절 표현을 검수합니다.
- 자동 생성·수집 자료는 검수 전 학생에게 노출되지 않도록 상태와 권한을 둡니다.
- 중복 제거, 품질 점검, 승인·반려, 재생성·수정 이력을 설계합니다.
- 매일 제공할 자료가 준비되지 않은 경우의 대체 콘텐츠와 운영 절차를 마련합니다.

**산출물**: 콘텐츠 운영 흐름, 검수 기준표, 샘플 콘텐츠, 공급 실패 대응 절차.

**완료 기준**: 실제 샘플 자료가 정한 기준에 따라 검수·게시되고 사용자에게 전달됩니다.

### 9단계. 통합 검증과 사용성 확인

검증은 목적에 맞는 범위로 합의해 진행합니다. 코드 변경이 없거나 위험이 낮은 변경에 일률적으로 큰 테스트를 적용하지 않습니다.

**검증 항목**

- 요구사항 및 인수 기준과 실제 동작의 일치
- 핵심 사용자 여정과 주요 실패·복구 흐름
- 콘텐츠 정확성, 출처 표시, 모바일 화면과 접근성
- 권한 우회, 입력 검증, 개인정보 노출 등 보안 관련 동작
- 매일 콘텐츠를 생성·게시·제공하는 운영 흐름
- 필요한 경우 성능, 브라우저 호환성, 백업 복구

**산출물**: 수행한 검증과 결과, 재현 가능한 결함, 사용자 피드백, 수정 목록.

**완료 기준**: 출시 차단 결함을 해결했거나 명시적으로 출시 여부를 결정했고, 미해결 위험과 제한 사항을 알고 있습니다.

### 10단계. 출시 준비와 배포

**할 일**

- 배포 환경, 도메인·HTTPS, 데이터베이스 백업, 비밀정보 관리, 권한을 준비합니다.
- 배포 전 데이터 변경·마이그레이션·롤백 영향을 확인합니다.
- 로그, 오류 알림, 서비스 상태 확인, 비용·AI 사용량 모니터링을 구성합니다.
- 장애 대응 담당과 연락 절차, 백업 복구 절차를 확인합니다.
- 소규모 사용자에게 먼저 공개할지, 단계적으로 확대할지 결정합니다.
- 배포 후 핵심 여정과 자료 공급이 정상인지 점검합니다.

**산출물**: 배포 체크리스트, 운영 안내, 롤백·복구 절차, 출시 기록.

**완료 기준**: 배포 후 이상을 감지하고 영향 범위를 파악하며 복구할 방법이 검토되어 있습니다.

### 11단계. 운영과 개선

**할 일**

- 자료 생성·검수·게시 성공 여부와 사용자 학습 흐름을 정기적으로 확인합니다.
- 학습 시작·완료·재방문 지표를 개인정보 최소 수집 원칙에 맞춰 확인합니다.
- 학생과 보호자 피드백, 오류 신고와 콘텐츠 수정 이력을 검토합니다.
- 문제의 원인을 콘텐츠, UX, 기술, 알림, 학습 난이도로 나누어 개선안을 정합니다.
- 가설과 결과를 기록하고 다음 우선순위에 반영합니다.

**산출물**: 운영 지표와 피드백 요약, 우선순위가 정리된 개선 목록, 다음 작업 범위.

**완료 기준**: 관찰 결과가 다음 기획·구현 주기의 결정으로 연결됩니다. 이후 2~11단계를 반복합니다.
