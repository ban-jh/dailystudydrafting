# 1단계 — 현재 상태, 목표 및 정보구조 초안

> 상태: 사용자 목표를 반영한 초안. 화면 이름과 메뉴는 기획 기준이며, 상세 요구사항·권한·MVP 범위 확정 전까지 제안으로 취급합니다.
>
> 기준일: 2026-11-05

## 1. 프로젝트 현재 상태

### 1.1 저장소 확인 결과

| 구분 | 확인 결과 | 판단 |
|---|---|---|
| 제품 문서 | `README.md`, `screen-design.md`, `architecture.md`가 있음 | 기획·화면·기술 설계 초안은 존재함 |
| 프로토타입/참고 자료 | `screen-spec/`, `storyboard/`, HTML 설계 파일이 있음 | 화면 구조를 검토할 참고 자료가 있음 |
| 웹 애플리케이션 코드 | Vue/TypeScript 소스, `package.json`을 찾지 못함 | 프론트엔드 구현 전 상태 |
| 백엔드 애플리케이션 코드 | Java 소스, `pom.xml`/Gradle 빌드 파일을 찾지 못함 | 백엔드 구현 전 상태 |
| 데이터베이스 구현 | SQL 마이그레이션/스키마 파일을 찾지 못함 | 데이터 모델은 설계 초안이며 구현되지 않음 |
| 테스트 코드 | 구현 소스 및 테스트 기반을 찾지 못함 | 테스트 계획은 요구사항과 구현 기반 확정 후 작성할 상태 |

위 판단은 현재 저장소에서 일반적인 Vue·Java·SQL 구현 파일을 검색한 결과입니다. 다른 저장소나 별도 브랜치에 실제 코드가 있다면 이후 현황 조사에서 추가로 대조해야 합니다.

### 1.2 기존 문서의 범위와 차이

- `architecture.md`는 학생용 요약·과목·퀴즈·오답노트, 관리자 콘텐츠 생성·검수, AI·크롤링, 배포 구조를 제안합니다.
- `screen-design.md`는 학생 화면과 관리자 콘텐츠 생성·검수·크롤링 화면을 상세히 설명합니다.
- 기존 학생 라우트는 대시보드, 과목/단원, 요약, 문제 풀이, 오답노트, 통계, 프로필 중심입니다.
- **보호자가 자녀 진도를 확인하는 화면과 자녀 연결·권한 흐름은 기존 화면·아키텍처에 구체적으로 없습니다.**
- **학교·학년별 학습 일정 생성과 학생별 일일 학습 배정 구조도 구체적으로 없습니다.** USER에 학교·학년 값은 초안으로 있지만, 일정·학급·보호자 연결 모델은 정의되어 있지 않습니다.
- 기존 아키텍처에서는 오답노트가 Phase 2, 관리자 통계·사용자 관리가 Phase 3에 배치되어 있습니다. 사용자가 밝힌 목표에서는 오답 재학습과 학교·학년 일정 운영이 핵심이므로 우선순위를 다시 정해야 합니다.
- 기존 문서에서 요약은 학생의 AI 생성 요청 API와 관리자 콘텐츠 관리가 함께 제안됩니다. 목표에 맞는 검수·게시 정책을 정한 후 학생은 게시된 자료를 학습하고 운영자는 콘텐츠를 생산·관리하는 역할로 경계를 명확히 해야 합니다.

## 2. 사용자가 확정한 서비스 목표

현재 합의된 목표는 다음과 같습니다.

> 중학생과 고등학생이 매일 학습 진도에 맞춰 공부할 수 있도록 요약 학습 내용과 문제를 제공한다. 틀린 문제는 오답으로 분류하고 이후 다시 제공하여 복습할 수 있게 한다. 학부모는 자녀의 학습 진도를 확인한다. 관리자는 학교와 학년에 따른 학습 일정을 만들고, AI 생성·크롤링·직접 등록 화면을 통해 학습 콘텐츠를 생산하고 관리한다.

이 목표를 기준으로 세 역할의 정보구조를 제안합니다.

## 3. 프론트엔드 메뉴 구조와 화면 정의

아래 경로는 구조를 설명하기 위한 **제안 라우트**입니다. 기존 `architecture.md`와 `screen-design.md`의 라우트가 일부 다르므로 이 문서에서 MVP 사용자 흐름을 기준으로 정리했으며, 최종 URL은 라우터 설계 단계에서 확정합니다.

### 3.1 공통·인증

| 메뉴 카테고리 | 화면명 | 제안 경로 | 화면 정의 |
|---|---|---|---|
| 인증 | 로그인 | `/login` | 학생·학부모·관리자가 계정으로 로그인하고 역할별 시작 화면으로 이동한다. |
| 인증 | 회원가입 | `/signup` | 허용된 사용자 유형과 기본 학년·학교 정보를 입력해 계정을 만든다. 가입 방식과 대상 역할은 정책 결정이 필요하다. |
| 공통 계정 | 내 프로필·설정 | `/my-page` | 계정 정보와 비밀번호, 알림 등 허용된 개인 설정을 확인·수정한다. |

### 3.2 학생 메뉴

| 메뉴 카테고리 | 화면명 | 제안 경로 | 화면 정의 |
|---|---|---|---|
| 오늘의 학습 | 오늘의 학습 | `/dashboard` | 학교·학년·진도에 배정된 오늘의 요약과 문제, 완료 여부, 이어하기, 복습할 오답을 한눈에 보여준다. |
| 학습 계획 | 과목·단원별 진도 | `/subjects` | 학생에게 적용된 과목·단원과 현재 학습 위치, 다음 학습 항목을 보여준다. |
| 학습 자료 | 요약 학습 | `/summaries/:summaryId` | 오늘 일정 또는 과목·단원에서 선택한 게시된 요약을 읽고 핵심 내용을 확인한다. 학습 완료 처리를 제공한다. |
| 문제 풀이 | 오늘의 문제 | `/quizzes/today` | 오늘 배정된 문제를 풀고 제출한다. 정답·오답 결과와 해설을 확인하고 풀이 결과를 저장한다. |
| 오답 복습 | 오답노트 | `/wrong-answers` | 틀린 문제를 과목·단원·상태별로 모아보고 재풀이할 항목을 선택한다. |
| 오답 복습 | 오답 다시 풀기 | `/wrong-answers/:attemptId/retry` | 기존 오답을 다시 제시하고 재풀이 결과와 복습 상태를 기록한다. |
| 학습 기록 | 내 학습 현황 | `/statistics` | 기간별 완료 기록, 과목·단원 진도, 문제 풀이 및 오답 복습 추이를 확인한다. |

**학생 내비게이션 제안:** 모바일에서는 `오늘의 학습`, `진도`, `문제`, `오답`, `기록`을 우선 노출하고 프로필은 계정 메뉴로 둡니다. 기존 `실생활 영어`, 배지·포인트는 핵심 학습 흐름과 MVP 범위를 확인한 뒤 포함 여부를 결정합니다.

### 3.3 학부모 메뉴

| 메뉴 카테고리 | 화면명 | 제안 경로 | 화면 정의 |
|---|---|---|---|
| 자녀 현황 | 학부모 대시보드 | `/parent/dashboard` | 연결된 자녀의 오늘 학습 배정·진행·완료 상태와 최근 요약을 보여준다. |
| 자녀 현황 | 자녀별 진도 | `/parent/children/:childId/progress` | 자녀가 학교·학년 일정에 따라 어느 과목·단원까지 학습했는지 확인한다. |
| 자녀 현황 | 학습 기록 | `/parent/children/:childId/history` | 기간을 선택해 요약·문제 완료 내역과 학습 빈도, 오답 복습 현황을 확인한다. |
| 자녀 관리 | 자녀 연결·전환 | `/parent/children` | 보호자 계정과 자녀 계정을 안전하게 연결하고 여러 자녀가 있을 때 조회 대상을 전환한다. |

학부모에게 완료 여부, 정답률, 개별 답안 중 어디까지 공개할지와 자녀 연결·동의 절차는 별도 정책 결정이 필요합니다.

### 3.4 관리자 메뉴

| 메뉴 카테고리 | 화면명 | 제안 경로 | 화면 정의 |

| 콘텐츠 관리 | 콘텐츠 라이브러리 | `/admin/contents` | 요약·문제 콘텐츠를 학교·학년·과목·단원·출처·검수 상태로 조회하고 편집한다. |
| 콘텐츠 생산 | AI 생성 | `/admin/contents/create/ai` | 대상 학년·진도·학습 목표·유형을 지정해 요약 또는 문제 초안을 생성한다. 생성물은 검수 전까지 학생에게 노출하지 않는 정책을 제안한다. |
| 콘텐츠 생산 | 크롤링·자료 수집 | `/admin/contents/create/crawl` | 허용된 출처와 범위를 설정해 자료를 수집하고 출처·수집 이력과 초안 결과를 확인한다. |
| 콘텐츠 생산 | 직접 등록 | `/admin/contents/create/manual` | 관리자가 요약 또는 문제를 직접 작성·수정하고 과목·단원·대상 학년을 연결한다. |
| 콘텐츠 검수 | 검수 대기함 | `/admin/review` | AI·수집·직접 등록된 콘텐츠의 정확성, 학년 적합성, 출처, 정답·해설을 확인해 승인·수정·반려한다. |
| 콘텐츠 게시 | 게시·배정 관리 | `/admin/publications` | 승인된 자료를 대상 일정에 게시하고 배정 결과·게시 기간을 관리한다. |
| 운영 관리 | 사용자·권한 관리 | `/admin/users` | 학생·학부모 계정, 자녀 연결, 관리자 권한을 관리한다. 세부 역할 분리는 결정이 필요하다. |
| 운영 관리 | 작업·수집 이력 | `/admin/operations` | AI 생성·크롤링 작업의 실행 상태, 오류, 결과와 콘텐츠 변경 이력을 확인한다. |

**관리자 업무 흐름 제안:** 학교·학년 및 교육과정 확인 → 일정 초안 생성 → 요약·문제 생산/수집 → 검수·승인 → 일정에 연결해 게시 → 학생 제공 상태 확인.

## 4. 백엔드 기능 구조도

백엔드는 화면 메뉴 대신 API와 도메인 책임으로 구성합니다. 아래는 프론트 화면이 어떤 서버 기능·데이터에 연결될지 보여주는 **백엔드 기능 구조 초안**입니다. 정확한 패키지·API 이름과 데이터 모델은 아키텍처 단계에서 확정합니다.

```text
Daily Study Backend
├── 인증·사용자·권한
│   ├── 로그인/토큰/세션
│   ├── 학생·학부모·관리자 프로필 및 역할
│   └── 보호자-자녀 연결, 동의·해제, 접근 범위 확인
├── 학교·교육과정
│   ├── 학교·학년도·학년(필요 시 학급)
│   ├── 교육과정·과목·단원·진도 기준
│   └── 학생의 학교·학년·교육과정 소속
├── 학습 일정·배정
│   ├── 학교·학년 대상 일정 템플릿
│   ├── 날짜별 요약·문제 연결 및 게시 기간
│   ├── 대상 학생에게 일일 학습 배정
│   └── 오늘의 자료 조회, 미배정·변경 이력 처리
├── 콘텐츠 관리
│   ├── 요약·문제 콘텐츠 저장, 버전·출처·상태
│   ├── AI 생성 작업
│   ├── 허용 출처 크롤링·수집 작업
│   ├── 직접 등록·수정·파일 일괄 등록(필요 시)
│   └── 검수·승인·반려·게시·보관
├── 학생 학습
│   ├── 오늘의 학습·과목·단원 자료 조회
│   ├── 요약 읽기 및 학습 완료 기록
│   ├── 문제 풀이 제출·채점·해설
│   └── 학습 이력·진도 집계
├── 오답 복습
│   ├── 오답 생성·목록·필터
│   ├── 재풀이 배정·결과 저장
│   └── 복습 완료/유지 상태 관리
├── 학부모 조회
│   ├── 연결된 자녀 목록·선택
│   ├── 자녀 오늘/기간별 학습 현황
│   └── 자녀 과목별 진도·기록 (허용된 범위만)
└── 관리자 운영·감사
    ├── 일정·콘텐츠·사용자 운영 API
    ├── AI/크롤링 작업 상태·오류·사용량
    └── 승인·게시·권한 변경 감사 기록
```

### 4.1 화면과 백엔드 책임 연결

| 화면 영역 | 백엔드 책임 | 현재 아키텍처와의 관계 |
|---|---|---|
| 학생 오늘의 학습·요약 | 배정된 오늘 자료 조회, 콘텐츠 게시 상태, 완료 기록 | `/api/dashboard`, `/api/summaries` 초안 재사용 가능. 날짜·배정 기준 추가 필요 |
| 학생 문제·오답 | 승인 문제 제공, 풀이·채점, 오답 재제공 상태 | `quiz`, `QuizAttempt`, `WrongNoteService` 초안 존재. 재제공 일정·상태 보강 필요 |
| 학생 진도·학습 기록 | 학교·학년 계획 대비 진도, 완료 집계 | `study` 초안 존재. 계획 대비 진도 기준 추가 필요 |
| 학부모 현황 | 연결 검증 후 자녀 데이터 범위 조회 | 기존에 전용 도메인/API가 없어 신설 필요 |
| 관리자 일정 | 학교·학년 계획 생성·수정·학생 배정 | 기존 설계에 전용 일정 도메인/API가 없어 신설 필요 |
| 관리자 콘텐츠 생산 | 요약·문제 AI/수집/수동 생산, 출처·상태 기록 | 문제 생성 API는 초안에 있음. 요약 포함 공통 운영 흐름과 게시 연결 보강 필요 |
| 관리자 검수·게시 | 상태 전이, 권한, 변경 이력, 학생 노출 제어 | 퀴즈 승인 초안은 있음. 요약 및 일정 게시까지 확장 필요 |

### 4.2 API 영역 후보

API는 설계 시작을 돕는 이름 예시이며 구현 계약이 아닙니다.

- 학생: `GET /api/me/today`, `GET /api/subjects`, `GET /api/summaries/{id}`, `POST /api/quiz-attempts`, `GET /api/quiz-attempts/wrong`, `POST /api/quiz-attempts/wrong/retry`
- 학부모: `GET /api/parent/children`, `GET /api/parent/children/{childId}/progress`, `GET /api/parent/children/{childId}/history`
- 관리자 학습 구조/일정: `/api/admin/schools`, `/api/admin/curriculum`, `/api/admin/schedules`, `/api/admin/assignments`
- 관리자 콘텐츠 작업: `/api/admin/contents`, `/api/admin/content-jobs/ai`, `/api/admin/content-jobs/crawl`, `/api/admin/contents/manual`, `/api/admin/reviews`, `/api/admin/publications`

## 5. 초안과 사용자 목표의 우선순위 정합성

| 항목 | 기존 설계 초안 | 현재 목표 기준의 제안 |
|---|---|---|
| 매일 일정 기반 요약·문제 | 과목/단원 콘텐츠 조회와 AI 요약 중심 | 학교·학년 진도에 따라 날짜별 자료를 배정하는 흐름을 핵심으로 구체화 |
| 오답 다시 제공 | 오답노트·재풀이가 후속 Phase에 배치됨 | 핵심 목표에 포함하여 MVP 우선순위를 재검토 |
| 학부모 진도 확인 | 전용 화면·API 흐름이 뚜렷하지 않음 | 보호자 포털과 연결·권한 정책을 새로 설계 |
| 학교·학년 일정 | 사용자 학교·학년 필드와 과목·단원 초안은 있음 | 일정 템플릿, 배정, 대상 그룹, 게시 이력을 새로 설계 |
| AI·크롤링·직접 등록 | 문제 생산 화면에 구체적 초안이 있음 | 요약과 문제 모두 생산·검수·일정 연결 범위에 포함할지 결정 |
| 콘텐츠 검수 | 문제는 PENDING 검수 후 게시하는 흐름 | 학생 노출 콘텐츠 전반에 같은 승인 원칙을 적용할지 결정 |

## 6. 다음 결정 사항

이 문서는 현재 상태와 사용자 목표를 기록하고 정보구조 초안을 제안합니다. 이후 범위를 확정하기 전에 아래 항목을 결정해야 합니다.

1. “학습 진도”는 학교의 실제 수업 진도, 교육과정/교과서 단원 순서, 학생 개인 진도 중 무엇을 기준으로 삼을지.
2. 일정 적용 단위는 학교 전체·학년·학급 중 어디까지 필요한지, 학교별 진도 차이를 누가 입력할지.
3. 일일 자료는 날짜 고정 공개인지, 학생이 완료한 속도에 따라 다음 자료를 푸는 방식인지.
4. 요약과 문제를 모두 매일 필수 제공할지, 과목·요일별로 다르게 배정할지.
5. 오답을 어떤 주기와 조건으로 다시 제공하고, 복습 완료를 어떻게 판단할지.
6. 학부모가 자녀 계정을 연결하는 방식, 여러 자녀 지원, 공개 가능한 학습 정보의 범위.
7. 학교별 관리자와 전체 관리자를 구분할지, 콘텐츠 검수 권한을 어떻게 나눌지.
8. AI·크롤링·직접 등록이 요약과 문제 모두에 적용되는지, 크롤링 허용 출처와 검수 책임은 무엇인지.
9. MVP에서 학교/학년 일정, 학생 오답 복습, 학부모 진도 화면을 모두 첫 출시 범위로 포함할지.
10. 첫 과목·학년, 하루 학습 분량, 콘텐츠 공급 인력·운영 제약 및 성공 지표.
